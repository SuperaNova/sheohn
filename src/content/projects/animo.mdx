## Overview

AniMo pairs smallholder farmers with buyers and a driver network so produce does not sit around waiting for a middleman. I managed the project and built the backend: Firebase, Cloud Functions, and a Genkit flow that asks Gemini on Vertex AI to match listings to requests.

### Background and context

We built this for the **GDG on Campus APAC Solution Challenge 2025**, a global AI hackathon run by Google Developer Groups and Hack2Skill. Student teams build Google AI-powered solutions for the United Nations' 17 Sustainable Development Goals (SDGs). AniMo targets Agriculture, Sustainability, and Responsible Consumption.

### The problem

Every year, a lot of edible food goes to waste because of broken supply chains, poor coordination, and limited access to distribution networks. Millions stay hungry despite available resources. Produce usually passes through several middlemen, such as distributors and retailers, before it reaches consumers. That adds time to the table and raises the chance of spoilage.

### The idea: harvest to hand

"Ani Mo" is a Filipino phrase meaning "your harvest". The platform connects smallholder farmers directly to buyers through community-based transport, with no traditional middlemen.

- **Farmers** manage live produce inventories and handle incoming buyer orders without market intermediaries.
- **Buyers** browse fresh produce, track order status in real time, and place custom requests for unlisted goods.
- **Drivers** make up the delivery network. They accept nearby tasks and do same-day farm-to-table deliveries.

### What I did

I was the project manager and the AI engineer, which on a four-person hackathon team means I drew the system diagram and then owned the middle of it: the Cloud Functions, the Firestore schema, and the Genkit flow that turns raw listings and buyer requests into match suggestions.

Three user interfaces hand state back and forth, so the platform sits on Google Cloud Platform and Firebase. The mobile client only presents data. Core logic, AI orchestration, and geospatial processing all run server-side.

### 1. Serverless orchestration and data flow

The backend logic runs entirely in Cloud Functions for Firebase. Each of the Produce Listing Service, Buyer Request Service, and Order Management Service runs independently, so it stays stable in high-traffic harvest seasons. Firestore is the primary NoSQL database for all reads and writes, and Firebase Authentication token verification protects access.

### 2. The AI matching engine (Vertex AI and Genkit)

> **The middleware challenge:** Connecting a surplus of dynamic, unstructured harvest data to specific buyer demands takes more than standard query logic.

The Genkit framework is deployed on Cloud Functions and runs an AI flow that calls Gemini models through the Vertex AI endpoint. This middleware reads existing database listings alongside custom buyer requests, analyzes them for matches, and writes suggestions back to Firestore.

### 3. Geospatial processing and routing

Efficient delivery is what keeps food from going to waste. The platform uses the Google Maps Platform, specifically the Geocoding API and Routes API. It processes spatial data in real time and suggests routes to drivers, which closes the distance between rural producers and urban consumers.

### 4. Deployment and observability

We deployed with the Firebase CLI. On a fully managed GCP environment, the platform handled load balancing and scaling for us. To keep the system stable during hackathon judging, we added **Google Cloud Operations**. Cloud Logging and Cloud Trace let us track the latency of the Vertex AI endpoint calls and check that the middleware wasn't timing out on complex matching.

## Technologies used

- **AI & Middleware:** Google Cloud AI, Genkit Framework, Gemini Models, Vertex AI.
- **Infrastructure & Backend:** Firebase (Firestore, Authentication, Cloud Storage), Google Cloud Operations (Cloud Logging, Cloud Monitoring, Cloud Trace).
- **Geospatial Data:** Google Maps SDK, Geocoding API, Routes API.
- **Client Interface:** Flutter, Flutterfire, Dart.

### Why this stack

In a 72-hour sprint, infrastructure overhead is the enemy of execution.

- **Serverless Backend (Firebase/GCP):** Picked so we did not have to provision servers by hand. Cloud Functions let us deploy separate backend services instantly, and Firestore gave us real-time, zero-config state sync across client devices.
- **Vertex AI vs. Direct API Calls:** We routed the matching engine through Vertex AI instead of public LLM endpoints. It integrates more tightly with GCP's IAM (Identity and Access Management) and has better native observability in the Google Cloud ecosystem.

## What we got done

The competition window was longer than 72 hours. Ours was not, because of coursework and org commitments, so we compressed the build into one sprint. We still shipped an MVP that did what we set out to do:

- **End-to-end flow:** Mock geospatial data and user requests went end to end through the Genkit middleware and came back as match suggestions in real time.
- **Zero downtime:** The serverless backend handled every concurrent read and write during the demo without dropping a state update.

---

## What we left rough

Three days means you pick speed over clean. This is what that cost:

- **Monolithic Cloud Functions:** To get state handoffs working before the deadline, logic that belongs in separate microservices went into a single compute block.
- **Cold start latency:** Cloud Functions had noticeable cold starts when triggering Gemini models through Vertex AI endpoints. Fixing that means pre-warming or moving to Cloud Run containers for sustained traffic.
- **Error handling and edge cases:** Rushed database writes sometimes lack full transactional validation. The system assumes the network is stable and does not handle network failures or race conditions between concurrent buyer requests.

### With three months instead of three days

1. **Add Redis caching:** Cache active nearby produce listings to cut Firestore read charges and lower the cost of model pipeline invocations.
2. **Integration testing:** Build automated pipelines that stress-test the state transitions between the driver routing logic and the AI matching services.
