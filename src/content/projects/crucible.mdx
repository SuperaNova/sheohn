## Overview

Crucible takes two 16-bit RPG item sprites and makes a third that is a believable mix of both. It is a chain of three agents, perception, reasoning and rendering, written in Python, with Google's Agent Development Kit (ADK) running the reasoning step and carrying state between stages.

### Why not just blend the pixels

> **The Goal:** How do we logically combine two game items to make a completely new one?

Average the pixels of a sword and a green gem and you get a brown smudge, not an emerald sword. We needed to merge what the items are, not what they look like at the pixel level. That meant going through language.

---

## Why not a VAE

The obvious approach to sprite fusion is to train a Variational Autoencoder (VAE) on the sprite dataset. You encode both sprites into latent vectors (`z_a` and `z_b`) and decode an interpolated point between them:

`z_fused = (1 - alpha) * z_a + alpha * z_b, alpha in [0, 1]`

A well-trained VAE enforces a smooth posterior (`q(z|x) ~ N(mu, sigma^2 I)`) via the Kullback-Leibler (KL) divergence term in the Evidence Lower Bound (ELBO) loss:

`L = E[log p(x|z)] - D_KL(q(z|x) || p(z))`

So points between $z_a$ and $z_b$ on the learned manifold are more likely to decode into coherent images than random interpolations in pixel space.

**The catch:** of about 89,400 raw sprites, only about 1,460 survived our cleaning heuristics. That is too few. The reconstruction loss dominates, the KL term collapses, and the posterior memorizes instead of generalizing, so the latent space is not smooth enough to interpolate across item categories.

So we stopped fighting the dataset and turned sprite fusion from a latent-manifold problem into a language-grounding problem.

---

## The three agents

We used the **RPG Framework** (Recaption, Plan, Generate) from _Yang et al., 2024_. Instead of one big script, perception (eyes), reasoning (brain) and rendering (brush) are separate agents that talk through shared state. Only the reasoning agent runs on Google ADK as an `LlmAgent`; the perception and rendering agents are role-defined units in plain Python, coordinated sequentially by a `Forge` orchestrator.

### 1. The Appraiser (vision)

Identity and appearance are split across two specialist vision models, because asking a small generative VLM "what is this?" on a 16×16 icon gets it wrong (it once called a blue gem a "health potion"):

- **Identity, SigLIP zero-shot (SO400M):** the sprite is scored against a fixed RPG vocabulary (`sword`, `gemstone`, `potion bottle`, …) with prompt ensembling. Closed-set classification is much more reliable than open generation at this resolution. (This is the SigLIP paper finally doing real work in the pipeline.)
- **Appearance, Moondream2 (1.8B VLM):** asked for colours, materials, and textures _only_, never to name the item or list parts. The structured `type + appearance` appraisal is written to shared state for the Smith.

### 2. The Master Smith (reasoning)

A text-only ADK `LlmAgent` reads the `{appraisal}` state and runs a four-step chain of thought. It picks the fused **archetype**, then writes a **part-by-part material blueprint**: for every component (blade, grip, gem, …) a `material`, `color`, source (`A`/`B`/`fused`), and surface `detail`. It does **not** write the diffusion prompt. It outputs a structured `parts` object checked against a schema. For example, _"the blade is polished gold inherited from B, the grip is oak wood from A"_, instead of a vague texture blend.

### 3. The Forger (rendering)

The Forger turns the Smith's blueprint into a diffusion prompt **deterministically**, one clause per part, so every material choice reaches the model. It then renders with Flux.1 (Pollinations) and runs the output through our post-processing code. An optional **ControlNet-Canny** path (SDXL, in the Colab notebook) conditions generation on the `structure_source` silhouette so the fused item keeps the chosen shape.

## Post-processing

Getting a big diffusion model to spit out a clean, 16-color RPG sprite required strict post-processing and hardware management.

### 1. Memory bounding

The two local vision models (SigLIP SO400M and Moondream2) run in `float16` and are loaded and unloaded **in sequence**, so peak VRAM stays around 3.5 GB, inside the 6 GB of a GTX 1660 Super. The reasoning and diffusion stages are API-only and use no GPU. Each generation samples a fresh random seed (logged to the console for traceability), so the same fusion can come out differently each time.

### 2. The pixel lattice

To turn detailed diffusion output into game assets, the Forger applies two operations:

- **Pixelation crunch:** The image is shrunk down to 32x32 using `Image.NEAREST` filtering, then scaled back up to 512x512. This wipes out gradient blending and forces a hard block grid whatever the source image.
- **Palette quantization:** We apply `Image.quantize(colors=16, method=MEDIANCUT)` _after_ the pixelation crunch. The 16-color palette then snaps to the already-hard pixel edges, which avoids the muddy in-between colors of ordinary downscaling.

## What shipped

- **Semantic material compositing.** The Master Smith started out drafting vague texture prompts and became a planner. It writes a per-part material blueprint (material, colour, source item, surface detail) that the Forger renders deterministically, instead of a blended-prompt average.
- **Identity via SigLIP.** Item recognition moved to a SigLIP zero-shot classifier over a fixed RPG vocabulary, which fixed the small-VLM mistakes (a blue gem read as a "health potion").
- **Shape via ControlNet.** An optional SDXL + ControlNet-Canny path conditions generation on the `structure_source` silhouette, so a fused item keeps the shape we chose.

## If someone picks this up

This was a finished mini-project. These are directions for anyone extending it, not active work.

- **Asynchronous decoupling.** The GPU-bound Forger dominates latency while the lighter agents idle. A message broker (Redis Pub/Sub or RabbitMQ), with perception and reasoning as producers and diffusion as a separate consumer, would let the pipeline clear a backlog at full hardware throughput.
- **A multimodal Smith.** The reasoning agent is text-only right now. Gemini is multimodal, so feeding it the actual sprites would ground the plan on pixels and match the RPG paper's multimodal CoT.
- **ControlNet as a core stage.** Move the notebook-only ControlNet path into the main pipeline so `structure_source` always drives the silhouette.
- **Ground-truth identity.** The dataset ships labels; using them for known sprites would give exact identity and reserve SigLIP zero-shot for unlabeled inputs.
- **Error handling.** Fail loudly when the Smith returns nothing instead of rendering a generic fallback, and add an optional fixed seed for reproducible fusions.
