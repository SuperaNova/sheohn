## Overview

Lexicon is the interpreter I wrote with a classmate for CS322, Programming Languages. The language, Lexor, was fully specified by the course: grammar, keywords and syntax were fixed. The job was to build a lexer, parser and evaluator that run that spec correctly, then make it usable from both a terminal and a browser.

### The constraint

Because the spec was fixed, the interpreter had to match it exactly, and it had to be efficient and safe.

---

## The interpreter

The engine lives in its own Rust workspace and follows the usual three stages.

- **Lexical analysis:** The Lexer implements Rust's standard `Iterator` trait, so the Parser can stream tokens. It looks ahead with `peek_char` to tell multi-character operators apart without consuming the stream.
- **Two parsing algorithms:** Parsing raw text into an Abstract Syntax Tree (AST) uses two algorithms. **Top-down recursive descent** handles structural blocks like `IF` and `FOR`. For Order of Operations in math, we wrote a **Pratt parser** driven by a central precedence table, so expressions bind without deeply nested logic.
- **The evaluator and memory:** The Evaluator walks the AST and keeps variables in an `Environment` struct that acts as local memory. Execution is decoupled from standard I/O through an injected `EnvironmentIO` trait, so the same evaluator runs in a terminal (CLI) or in a web browser without blocking threads.

## Publishing the Wasm build

To connect the Rust core to the web frontend, we set up a **GitHub Actions** pipeline.

Nobody compiles or moves binaries by hand. Whenever a new version tag is pushed to the repository, the workflow:

1. Compiles the Rust workspace targeting `wasm32-unknown-unknown`.
2. Packages the binary using `wasm-pack`.
3. Publishes the updated `@superanova/lexor_wasm` package directly to the registry.

The Web IDE always gets the latest compiler engine without a manual deploy.

## The web IDE

To show off the Lexor language, we built **Lexicon**, a lightweight, interactive Web IDE with **SolidJS**, **CodeMirror v6**, and **Tailwind CSS**.

### No servers

Instead of running user code on a server the way Replit does, the Wasm module runs in the visitor's browser. No round trip, no sandbox for us to secure, and the IDE sits on GitHub Pages for free.

### Input without blocking the page

To keep complex scripts from freezing the browser's main UI thread, the Wasm binary runs inside an isolated Web Worker.

Web Workers cannot reach the browser's DOM, so native `window.prompt()` fails. We wrote a custom asynchronous API bridge between the Wasm worker and the SolidJS main thread. When the interpreter hits a SCAN statement it pauses, posts a message to the main thread to show the input UI, and resumes with the answer. Standard I/O stays off the execution thread and the terminal feels interactive in the browser.
